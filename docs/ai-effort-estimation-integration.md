# Интеграция ИИ для оценки сроков и трудозатрат

Практический план внедрения в **свою** систему трекинга задач и времени.
Документ опирается на подход из
[How to Use AI for Project Effort Estimation](https://projectmanagementformula.com/how-to-use-ai-project-effort-estimation/)
и
[AI for Project Scheduling](https://projectmanagementformula.com/ai-for-project-scheduling/),
но переводит его из «промптов в ChatGPT» в продуктовую интеграцию: данные, API, UX, governance и замкнутый цикл обучения.

ИИ здесь **не заменяет** оценку и не «ставит дедлайн». Он даёт:

- исторический якорь (как у нас это уже получалось);
- диапазон, а не одну цифру;
- черновик WBS, зависимостей и рисков на ревью;
- непрерывный пересчёт прогноза по факту.

Владелец оценки и расписания — человек (PM / техлид). Система обязана уметь объяснить, **откуда** взялось число, и зафиксировать, **почему** его изменили.

## 1. Что внедряем, а что сознательно не внедряем

### 1.1. Три разные задачи (их нельзя смешивать)

| Задача | Вопрос | Что умеет ИИ хорошо | Что ИИ делает плохо |
|---|---|---|---|
| **Effort** | Сколько человеко-часов / story points на пакет работ? | Analogous estimation по своей истории, трёхточечная оценка, калибровка bias | Оценка «с нуля» без истории и без WBS |
| **Duration / schedule** | Когда закончим при данной команде, зависимостях и календаре? | CPM, ресурсные конфликты, what-if, раннее предупреждение срыва | Политика, «этот стейкхолдер тормозит согласование» |
| **Risk overlay** | Что модель не видит? | Структурировать риски и pessimistic-сценарий | Оргполитика, отношения с вендором, смена стратегии |

Effort ≠ duration. 80 часов на одного senior ≠ 2 календарные недели при 50% загрузке, отпусках и блокере на API партнёра. Слой планирования должен считать duration **отдельно**, из effort + capacity + dependencies.

### 1.2. Принципы (иначе получится уверенно неверная оценка)

1. **Сначала данные, потом модель.** Без сопоставимых estimate vs actual ИИ будет уверенно галлюцинировать.
2. **Сначала WBS, потом оценка.** Оценка «эпика целиком» даёт иллюзию точности.
3. **LLM — не калькулятор.** LLM хорош для декомпозиции, аналогий, рисков и текста. Числа по истории считает retrieval + статистика / ML, не «GPT сказал 3 недели».
4. **Параллельные оценки.** Человек и ИИ считают независимо, потом сходятся. Если сначала показать число ИИ — оно якорит команду (anchoring).
5. **Диапазон, не точка.** Optimistic / most likely / pessimistic → PERT → при зрелости Monte Carlo → P50 / P80 / P90.
6. **Override только с причиной.** Иначе ИИ обойдут при первом давлении спонсора.
7. **Context overlay.** Рядом с прогнозом всегда лежит то, чего в трекере нет: политика, вендор, регуляторика.
8. **Один пилот-сценарий, не «ИИ-оракул на всё».** Сначала baseline effort, потом мониторинг срыва, потом what-if и ресурсы.

### 1.3. Целевой пользовательский результат

На карточке **нового проекта / эпика / пакета работ** PM нажимает «Оценить с ИИ» и видит:

- 3–7 ближайших исторических аналогов (с фактом, не с планом);
- трёхточечную оценку effort и календарный прогноз при текущем составе команды;
- P50 / P80;
- топ-риски pessimistic-сценария;
- список вопросов, без ответов на которые оценка ненадёжна;
- кнопку «принять / скорректировать / отклонить» с обязательным комментарием при расхождении.

Во время исполнения тот же объект еженедельно пересчитывает **оставшийся** срок по фактическому burn-rate и сигналит: «интеграционное тестирование на похожих проектах уезжало +40%».

## 2. Целевая архитектура

Не покупать отдельный «AI scheduler» и не кормить весь трекер в ChatGPT.
Свой трекер — преимущество: источник истины, UI и governance живут в одном месте.

```
┌─────────────────────────────────────────────────────────────────┐
│                     Трекер (source of truth)                    │
│  проекты, WBS, задачи, time logs, люди, навыки, календарь       │
└──────────────┬──────────────────────────────┬───────────────────┘
               │ события (задача закрыта,     │ запрос оценки /
               │ списано время, изменился     │ сценарий what-if
               │ scope)                       │
               ▼                              ▼
┌──────────────────────────┐    ┌─────────────────────────────────┐
│  Feature store / витрина │    │  Estimation service             │
│  «как было на самом деле»│    │                                 │
│  - пакеты работ          │    │  1. Analog retriever            │
│  - estimate vs actual    │    │  2. Calibrator (bias-факторы)   │
│  - эмбеддинги описаний   │    │  3. LLM reasoner (черновик)     │
│  - признаки проекта      │    │  4. Scheduler (CPM + capacity)  │
│                          │    │  5. Monte Carlo (позже)         │
└──────────────────────────┘    └──────────────┬──────────────────┘
                                               │
                                               ▼
                                ┌─────────────────────────────────┐
                                │  UX в трекере                   │
                                │  оценка, ревью, override,       │
                                │  context overlay, reforecast    │
                                └─────────────────────────────────┘
```

### 2.1. Два движка, не один

| Движок | Вход | Выход | Зачем |
|---|---|---|---|
| **Analog + calibrator** (детерминированная математика / простой ML) | признаки пакета + история | распределение часов, bias по типу работ | это и есть «оценка по нашей практике» |
| **LLM reasoner** | описание, команда, найденные аналоги, ограничения | WBS-черновик, зависимости-кандидаты, риски, вопросы, narrative | объясняет и дополняет, не подменяет цифру |

Правило сборки ответа:

1. Найти аналоги и посчитать статистический диапазон.
2. Отдать LLM **только** эти аналоги + карточку работы (не всю базу).
3. LLM комментирует, где статистика может врать, предлагает pessimistic-драйверы, не имеет права «перебить» P80 без явной пометки `llm_adjustment`.
4. Планировщик переводит effort в duration.
5. Человек утверждает.

Если аналогов мало — система **снижает confidence** и явно пишет: «оценка слабо опирается на историю, вес экспертного суждения выше». Это важнее, чем красивое число.

### 2.2. Что считать своим кодом, что — внешней моделью

| Компонент | Рекомендация |
|---|---|
| Хранение задач, времени, оценок, audit log | Свой трекер |
| Поиск похожих пакетов (эмбеддинги + фильтры) | Свой сервис; эмбеддинги — API модели |
| Калибровка (quantile, regression, bias по типу) | Свой код на витрине; на старте даже SQL + перцентили |
| LLM | внешний API (Claude / GPT) **через свой backend**, с красным списком полей |
| CPM / resource leveling / Monte Carlo | свой код или проверенная библиотека, не LLM |
| Промпты, версии моделей, логи запросов | свой prompt registry + trace id на каждой оценке |

Данные проектов **не** должны уезжать в потребительский ChatGPT руками PM. Канал один: backend трекера → провайдер с DPA, без обучения на ваших данных, с маскированием.

## 3. Фаза 0. Аудит данных (до выбора модели)

Статьи сходятся в одном: без этой фазы остальное вредно. ИИ усиливает и хорошую практику, и мусор.

### 3.1. Минимальный объём, после которого analog-оценка имеет смысл

Ориентир из методологии: **15–20 завершённых сопоставимых проектов или, лучше, 50–100 пакетов работ** одного класса (не «все задачи компании в одной куче»).

Считать нужно **пакеты работ** (epic / feature / work package), а не только проект целиком и не каждую 15-минутную задачку. Слишком крупно — не на чем учиться. Слишком мелко — шум и разный стиль нарезки задач.

### 3.2. Чеклист качества (пройти по факту, не по ощущению)

Для выборки закрытых проектов ответить «да/нет/частично»:

1. Есть **исходная** оценка (не перезаписанная под факт)?
2. Есть **факт** в тех же единицах (часы списаний, не «статус done»)?
3. Оценка и факт стыкуются на одном уровне WBS (не «оценили эпик, списали на подзадачи без связи»)?
4. Проекты размечены типом / доменом / стеком?
5. Известен состав команды (роли, seniority) на момент оценки?
6. Зафиксированы scope-change (что добавили и сколько это стоило)?
7. Time log пишется в процессе, а не «закрыли месяц потом на глазок»?
8. Есть простои: ожидание внешней системы, согласования, блокеры?
9. Календарь людей (отпуска, % аллокации) восстанавливается?
10. «Зелёные» статусы не врали: план не подгоняли под факт задним числом?

Каждый «нет» — либо поле, которое надо начать писать, либо ограничение, которое UI оценки обязан показывать как пониженный confidence.

### 3.3. Типичные болезни трекеров и что с ними делать

| Болезнь | Почему ломает ИИ | Что сделать в своей системе |
|---|---|---|
| Оценка перезаписывается | нельзя учить bias | `original_estimate` иммутабелен; дальше только `reforecast` |
| Списания без задачи / на «прочее» | факт дырявый | запрет списания вне WBS-узла; bucket `unallocated` виден в отчёте качества |
| Разный уровень декомпозиции | «похожие» пакеты несравнимы | канонический уровень `work_package` |
| Нет типа работ | смешаются багфикс, greenfield, интеграция | обязательный `work_type` |
| Нет стека / домена | аналоги по тексту врут | теги `domain`, `tech_stack` |
| Scope creep не отделён | модель думает, что оценка была «плохая», хотя меняли задачу | сущность `scope_change` с impact_hours |
| Героическое закрытие в конце периода | actual сдвинут | timestamp списания, алерт «>X часов задним числом» |

### 3.4. Выход фазы 0 — data scorecard

Одна страница на тип проектов (например «внедрение интеграций», «продуктовые фичи», «внутренние инструменты»):

- N закрытых пакетов;
- % пакетов с парой estimate+actual;
- median / P80 overrun;
- топ-3 фазы, которые систематически уезжают (часто это интеграция, UAT, data migration — ровно тот паттерн из статьи про scheduling);
- решение: **пилот на этом классе** / сначала чинить учёт / этот класс не оценивать ИИ.

Пилот брать там, где история **повторяема**. Новые для компании вещи — в режиме «LLM + эксперт, широкий интервал, низкий confidence».

## 4. Фаза 1. Каноническая модель данных в трекере

Пока этого нет, любой «чат с ИИ» — демо. Ниже — сущности, которые стоит добавить (названия можно адаптировать).

### 4.1. Уровни работ

```
Project
  └── WorkPackage          ← единица оценки и аналогов
        └── Task           ← единица исполнения и time log
              └── TimeEntry
```

Правило: **оцениваем WorkPackage, списываем на Task, агрегируем факт на WorkPackage**.

### 4.2. Карточка пакета, достаточная для оценки

Обязательные поля:

- `title`, `description`, `acceptance_criteria`
- `work_type` (feature, integration, migration, bugfix, research, infra, compliance, …)
- `domain`, `tech_stack[]`
- `complexity` (команда ставит **до** ИИ, иначе ИИ сам себе поставит сложность)
- `dependencies[]` (внутренние пакеты + внешние: вендор, регулятор, смежный отдел)
- `team_snapshot` на дату оценки: роли, seniority, `%` аллокации, familiarity со стеком (low/med/high)
- `constraints` (дедлайн снаружи, фиксированный состав, техдолг, security review)
- `novelty` (repeatable / similar / first-time) — явно снижает вес истории

### 4.3. Оценки как неизменяемая история, не одно поле

```
EstimateSnapshot
  id
  work_package_id
  created_at, created_by
  source: human | analog_model | llm | hybrid | committed
  unit: hours | days | story_points   // в пилоте лучше часы факта
  optimistic, most_likely, pessimistic
  pert_mean                          // (O + 4M + P) / 6
  p50, p80, p90                      // когда появится распределение
  analog_set_id                      // какие исторические пакеты вошли
  model_version, prompt_version
  assumptions[]                      // структурированный реестр
  risks[]                            // драйверы pessimistic
  open_questions[]
  confidence: high | medium | low
  context_overlay                    // свободный текст: «чего модель не видит»
```

Committed-оценка — отдельный снимок `source=committed`. Её нельзя тихо переписать: только новый snapshot + reason.

### 4.4. Факт и обучение

```
WorkPackageActual
  effort_hours_actual
  duration_calendar_days
  wait_hours                 // блокеры, не работа
  rework_hours               // если умеете маркировать
  scope_change_hours
  original_estimate_hours    // копия иммутабельного оригинала
  overrun_ratio              // actual / original (scope-adjusted)
```

`overrun_ratio` считать **дважды**: сырой и с вычетом официальных scope_change. Иначе модель накажет за то, что заказчик расширил рамки.

### 4.5. Качество данных как продукт, не как разовая выгрузка

Дашборд «можно ли верить ИИ»:

- доля задач с описанием > N символов;
- доля списаний старше 7 дней;
- доля пакетов без original_estimate;
- доля пакетов без work_type;
- completeness score по проекту — и **блок кнопки «Оценить»**, если score ниже порога, с конкретным «докажите вот эти поля».

Это важнее выбора LLM.

## 5. Фаза 2. Поиск аналогов и калибровка (можно без LLM)

Это самый большой ROI. Даже Excel-уровень уже бьёт чистый экспертный оптимизм, если показывать распределение факта, а не «в среднем 5 дней».

### 5.1. Как искать похожее

Два канала, потом пересечение:

1. **Жёсткие фильтры:** `work_type`, `domain`, `tech_stack` overlap, размер команды ±, `novelty`.
2. **Семантика:** эмбеддинг `title + description + acceptance_criteria`, kNN по закрытым пакетам.

Отдавать в UI не «похожесть 0.83», а **карточки аналогов**:

- что это было;
- original vs actual (effort и календарь);
- состав команды тогда;
- какие scope_change случились;
- короткая выжимка «почему похоже / чем отличается».

PM должен иметь право **выколоть** плохой аналог (другой вендор, другая команда). Выкол фиксируется в `analog_set`.

### 5.2. Как из аналогов сделать число

На старте, без ML-инженерии:

1. Взять 5–15 аналогов после фильтров.
2. Посчитать по `actual_hours` (лучше scope-adjusted) перцентили P20 / P50 / P80.
3. Это черновик O / M / P. Optimistic не P0 и не минимум-герой: P10–P20.
4. Посчитать PERT-mean: `(O + 4M + P) / 6`.
5. Отдельно показать **исторический bias** этого `work_type`: «интеграционные тесты у нас actual = 1.4 × estimate».

Калибратор — таблица, не нейросеть:

```
work_type × domain × seniority_mix → median_overrun, p80_overrun, sample_size
```

Если `sample_size < 8` — не применять калибровку молча, писать «мало наблюдений».

### 5.3. Когда подключать простой ML

Имеет смысл, когда на одном классе работ сотни пакетов и уже есть стабильные признаки. Кандидаты: градиентный бустинг / квантильная регрессия на признаках (размер описания, число зависимостей, novelty, стек, команда, наличие внешней интеграции).

Не начинать с этого. Сначала перцентили по аналогам + bias-таблица. Их можно объяснить аудитору и спонсору.

### 5.4. Перевод effort → duration

Входы планировщика (детерминированные):

- effort P50/P80 пакета;
- назначения и `%` аллокации;
- календарь (выходные, отпуска, ceremonies);
- зависимости (FS/SS + lag);
- wait-буфер на внешние зависимости (из истории wait_hours, не из оптимизма).

Выход: earliest/latest, slack, critical path, resource overallocation.

LLM может **предложить** зависимости по тексту. В граф они попадают только после галочки PM. Ожидаемая точность кандидат-зависимостей по индустрии далеко не 100% — закладывайте ревью, не автоприменение.

## 6. Фаза 3. LLM как reasoner: как с ним взаимодействовать

### 6.1. Где человек встречается с ИИ (роли)

| Роль | Что делает с ИИ | Чего не делает |
|---|---|---|
| PM | запускает оценку, ревьюит аналоги и риски, утверждает committed, ведёт context overlay | не отправляет сырой экспорт базы в чат |
| Техлид / исполнитель | независимо даёт свою трёхточку **до** просмотра ИИ; потом комментирует расхождения | не обязан соглашаться с моделью |
| Спонсор | видит P50/P80 и драйверы, не «одну дату» | не торгуется с моделью в обход PM |
| Админ данных | следит за scorecard, версиями модели, утечками полей | не «докручивает» прогноз вручную в проде |

### 6.2. Протокол оценки нового пакета (обязательная последовательность)

```
1. Человек пишет scope: описание, DoD, work_type, команда, novelty, constraints.
2. Система проверяет completeness. Если мало данных — стоп и список вопросов.
3. Команда (или техлид) вводит human three-point, UI ещё не показывает ИИ.
4. Analog retriever + calibrator считают машинный диапазон.
5. LLM получает карточку + аналоги (не всю историю) и возвращает:
   - комментарий к диапазону,
   - риски pessimistic,
   - скрытые работы (часто: тестовые стенды, миграция, согласования, rollback),
   - вопросы,
   - кандидаты зависимостей.
6. UI показывает split view: Human | Analog | Hybrid draft.
7. Расхождение > порога (например 25% по PERT-mean) → обязательный reconciliation note.
8. PM сохраняет committed + assumptions register + context overlay.
9. Планировщик кладёт пакет на календарь; критический путь и перегрузка видны сразу.
```

Порог расхождения и «кто имеет право закоммитить ниже P80» — это политика компании, её надо записать в регламент, не в промпт.

### 6.3. Контракт ответа LLM (JSON, не эссе)

Пример схемы, которую backend валидирует:

```json
{
  "hidden_work": [{"item": "нагрузочный тест на контуре staging", "why": "..."}],
  "dependency_candidates": [{"from": "...", "to": "...", "confidence": 0.6, "rationale": "..."}],
  "risks_pessimistic": [{"risk": "...", "how_it_extends_effort": "..."}],
  "questions_blocking_reliability": ["Нужен ли security review третьей стороной?"],
  "why_analogs_may_not_apply": ["В аналогах не было интеграции с 1С"],
  "suggested_overlay": "Смена CPO в Q3 не отражена в истории",
  "must_not": "не заменять p50/p80, посчитанные калибратором"
}
```

Если модель вернула свои часы — сохранить в `llm_adjustment` **отдельно** и не подменять analog P80 без флага в UI: «это мнение модели, не статистика».

### 6.4. Каркас промпта (системный, версионируемый)

Держать в коде, не в голове PM. Идея шаблона:

```
Ты — аналитик оценки в нашей компании, не оракул сроков.
Тебе дан пакет работ и ТОЛЬКО список исторических аналогов с actual hours.
Запрещено игнорировать аналоги и придумывать отраслевые «средние по рынку»,
если они противоречат фактам ниже.
Запрещено выдавать одну цифру.
Запрещено менять статистические p50/p80 — они уже посчитаны сервисом.
Твоя работа: найти дыры в scope, скрытые работы, почему аналоги могут врать,
риски pessimistic-сценария, вопросы, без которых оценка ненадёжна.
Команда: {team_snapshot}
Novelty: {novelty}
Constraints: {constraints}
Analog facts: {analog_table}
Acceptance criteria: {dod}
Ответ строго JSON по схеме.
```

Практика из шаблонов Project Management Formula, которую стоит сохранить:

- всегда three-point, никогда single-point в коммуникации со спонсором;
- всегда assumptions register;
- всегда «какие вопросы закрыть, чтобы сузить диапазон».

### 6.5. Готовые сценарии в UI (не свободный чат в проде)

Свободный чат быстро разъезжается и не логируется. Лучше кнопки:

1. **Оценить пакет** — основной поток выше.
2. **Добить WBS** — разложить пакет на подпакеты с критерием готовности; оценка только после подтверждения нарезки.
3. **Найти скрытые зависимости** — кандидаты, PM подтверждает.
4. **Стресс-тест плана** — «что ломает pessimistic».
5. **What-if** — «+1 разработчик с недели 6», «вендор +3 недели»: считает планировщик, LLM описывает trade-off человеческим языком.
6. **Еженедельный reforecast** — по actuals, без новой «творческой» оценки с нуля.
7. **Разбор закрытого пакета** — почему actual разошёлся; это топливо для калибратора и overlay.

Для высоких ставок: прогнать reasoner на двух моделях и показать расхождение как сигнал неопределённости входов, а не как «какая модель умнее».

### 6.6. Context overlay — обязательное поле рядом с гантом

Короткий живой текст (и теги), который модель **не выводит из трекера**:

- доверие спонсора / политический ветер;
- состояние вендора;
- параллельный орг. change;
- регулятор, который ещё не дал рамку;
- «команда первый раз в домене, хотя стек знакомый».

Overlay входит в committed-снимок и в еженедельный статус. Если overlay пустой, а `novelty=first-time` — warning.

## 7. Фаза 4. Расписание, мониторинг, what-if

Когда effort-контур живой, наращивать scheduling — иначе оценка часов не станет датой.

### 7.1. Baseline

После committed-оценок система строит baseline: даты, critical path, гистограмма загрузки. Baseline **замораживается**. Дальше actual и reforecast сравниваются с ним, а не «подкрученный план всегда зелёный».

### 7.2. Мониторинг (часто более выгодный, чем идеальный план)

Раз в период (у вас это может быть при каждом закрытии задачи / ежедневном агрегате):

- burn-rate vs план по пакету;
- рост wait_hours;
- slip по пакетам, похожим на текущий critical path;
- ресурс > 100%;
- scope_change без переоценки пакета.

Алерт должен звучать как в статье про scheduling: не «проект красный», а «на 14 похожих интеграциях тестовая фаза уезжала ~40%; у нас осталось 8 дней плана и 30% тестов». Это actionable.

Идентификация задержки на несколько недель раньше статус-репорта — главный операционный выигрыш, не «магический kickoff».

### 7.3. What-if

Сценарии — клоны графа, не правки baseline:

- выкинуть scope;
- добавить FTE на некритичный / критичный путь;
- сдвиг внешнего dependency;
- разрез UAT.

Считать движком расписания. LLM подписывает сравнение для комитета: три пути, trade-off scope/срок/риск. Спонсор выбирает путь, система сохраняет выбранный scenario id.

### 7.4. Monte Carlo — не день первый

Когда трёхточки стабильно пишутся и actuals копятся:

- для каждого пакета распределение из истории (не «PM на глаз O/M/P»);
- N прогонов по графу с зависимостями;
- спонсору: «P50 = дата A, P80 = дата B, три главных драйвера хвоста».

Контингенси ставить как выбор точки на распределении под риск-аппетит (регуляторный релиз ≠ внутренний инструмент), не как вечный «+15%».

## 8. Governance: чтобы ИИ не обошли и не обожествили

### 8.1. Правила коммита даты

- В комитет уходит **диапазон** + выбранный confidence (например commit = P80).
- Рядом: human estimate, analog estimate, список аналогов, overlay.
- Если commit < analog P50 — требуется письменное «почему этот проект легче истории» и что сделаем, если не легче.
- Если commit приняли под давлением даты спонсора — это не «уточнение», это `override_reason=business_date`, и риск автоматически поднимается.

### 8.2. Automation bias

Цветной уверенный виджет опаснее кривой экспертной оценки: с ним труднее спорить. В UI:

- запретить зелёный бейдж при `confidence=low` или `sample_size < N`;
- всегда показывать аналоги и actual, не только «ИИ: 27 недель»;
- кнопка «почему так» открывает расчёт, а не маркетинговый текст.

### 8.3. Приватность и минимизация

В промпт/эмбеддинги не класть:

- персональные данные сверх роли и seniority (никаких зарплат, больничных формулировок);
- содержимое клиентских тайн, если пакет можно описать обезличенно;
- комментарии вида «Иванов тормозит».

Эмбеддинги и трейсы LLM — с TTL и access log. Оценка — юридически значимый артефакт, как смета.

### 8.4. Сохранение экспертности

Раз в N закрытых пакетов команда оценивает **вслепую**, без ИИ, для калибровки людей и проверки, что модель не деградировала. ИИ, который никто не умеет оспорить, вреден.

## 9. Пошаговый план внедрения (поставки, не «и сразу Copilot»)

Каждый шаг заканчивается **проверяемым артефактом**. Следующий не начинать, пока артефакта нет.

### Шаг 1. Зафиксировать единицу оценки

- Ввести `WorkPackage` как канон.
- Запретить committed-дату проекта без декомпозиции до этого уровня.
- Артефакт: 1 пилотный проект, нарезанный целиком.

### Шаг 2. Заморозить original estimate и начать писать факт честно

- Иммутабельный original.
- Time log только на задачи пакета.
- Поле scope_change.
- Артефакт: на пилоте пара estimate/actual собирается автоматически.

### Шаг 3. Разметка истории

- Ретроспективно проставить `work_type`, `domain`, `tech_stack`, связать списания с пакетами там, где возможно.
- Не пытаться «вычистить всю компанию». Взять один класс работ.
- Артефакт: scorecard и список из ≥15–20 сопоставимых пакетов (лучше больше).

### Шаг 4. Analog-панель без LLM

- kNN + фильтры + перцентили + bias-таблица.
- PM видит аналоги руками, ещё без «магии».
- Артефакт: на 5 новых пакетах люди говорят, что аналоги узнаваемые. Если нет — чинить поиск, не клеить LLM.

### Шаг 5. Протокол двойной оценки

- Форма human three-point.
- Split view и reconciliation note.
- Артефакт: регламент на одной странице, согласованный с теми, кто несёт дедлайн.

### Шаг 6. LLM-reasoner в том же экране

- JSON-контракт, prompt versioning, красный список полей.
- Кнопки сценариев, не свободный чат.
- Артефакт: 10 прогонов, где скрытые работы/риски признаны полезными хотя бы в половине случаев ( qualititive review техлида).

### Шаг 7. Effort → schedule

- Календари, аллокации, зависимости, critical path, overallocation.
- Кандидаты зависимостей от LLM — только как черновик.
- Артефакт: baseline пилотного проекта, который совпадает с тем, что PM готов показать спонсору.

### Шаг 8. Reforecast по факту

- Еженедельный (или по событию) пересчёт остатка.
- Алерты «фаза X обычно уезжает».
- Артефакт: хотя бы один ранний алерт, который команда подтвердила как полезный, а не шум.

### Шаг 9. What-if и вероятностный язык для спонсора

- Сценарии.
- При готовности — Monte Carlo.
- Артефакт: шаблон слайда «P50/P80 + драйверы + overlay», которым реально пользуются, а не Gantt с одной датой.

### Шаг 10. Замкнутый цикл

- При закрытии пакета: actual, wait, rework, scope_change, разбор «почему разошлись».
- Обновление bias-таблицы / выборки аналогов.
- Раз в цикл — ревизия промпта и порогов.
- Артефакт: график `|actual − committed|` по пилотному классу работ; цель — сужение ошибки и калибровка P80 (в ~80% случаев actual ≤ P80).

## 10. Как понять, что это работает

Считать **до** включения ИИ (baseline) и после, на одном классе работ:

| Метрика | Зачем |
|---|---|
| MAE / MAPE committed effort vs actual (scope-adjusted) | точность |
| Калибровка P80: доля пакетов с actual ≤ P80 | не врём ли диапазоном |
| Bias: median(actual/estimate) по work_type | ловим оптимизм |
| Lead time от «есть scope» до «есть committed» | скорость планирования |
| Доля оценок с заполненным overlay и assumptions | дисциплина |
| Доля override без reason | обход системы |
| Time-to-detect slip (план vs факт по фазе) | ценность мониторинга |
| % пакетов с валидной парой original+actual | здоровье топлива модели |

Не KPI: «количество запросов к LLM». Можно много спрашивать и ничего не калить.

## 11. Ошибки, которые стоит заранее запретить

1. Оценить проект одной кнопкой без WBS.
2. Отдать LLM роль калькулятора часов.
3. Показать число ИИ команде до их оценки.
4. Перезаписать original, чтобы «история выглядела хорошо».
5. Учить модель на плане, а не на actual.
6. Смешать first-time R&D с сотым лендингом в одном analog-пуле.
7. Поставить дедлайн спонсора в модель как «most likely».
8. Автоприменять зависимости и даты.
9. Игнорировать wait/external: получится оценка кодирования, а не проекта.
10. Не закрывать цикл после релиза — тогда каждый проект снова с нуля.

---

## 12. Рекомендуемый минимальный контур (если делать только необходимое)

Если вырезать всё необязательное, жизнеспособный продукт — это:

1. Канонический WorkPackage + иммутабельный original + честный actual.
2. Поиск аналогов + перцентили + bias по типу работ.
3. Экран двойной оценки с reconciliation.
4. LLM только для дыр в scope, рисков и вопросов (JSON).
5. Простой планировщик effort→даты при известных аллокациях.
6. Еженедельный reforecast.
7. Overlay + assumptions как обязательные поля committed-оценки.

Этого достаточно, чтобы получить эффект статей (исторический якорь против planning fallacy, диапазоны вместо точки, ранняя сигнализация срыва) **на своих данных**, без ожидания «платформы, которая сама всё распланирует».

## 13. Карта решений «что писать в трекере завтра»

Короткий backlog для разработки (порядок = приоритет):

1. Модель `WorkPackage`, `EstimateSnapshot`, `ScopeChange`, `WorkPackageActual`.
2. Запрет затирания original_estimate.
3. Scorecard качества данных.
4. Витрина закрытых пакетов (ETL из текущих таблиц задач/списаний).
5. Analog search API + UI «похожие поставки».
6. Bias table + PERT.
7. Human vs analog split + mandatory reason.
8. LLM gateway + schema validation + prompt versions + redaction.
9. Кнопки: hidden work / questions / dependency candidates.
10. Capacity calendars + CPM.
11. Baseline freeze + reforecast job.
12. Alerts по историческому overrun фазы.
13. Scenario clones + comparison view.
14. Monte Carlo на исторических распределениях.

Пункты 1–7 уже меняют качество оценок даже при выключенном LLM. Пункты 8–9 ускоряют мысль. Пункты 10–14 переводят часы в управляемые сроки.
